# 1. Минимум теории: что происходит внутри

Эта глава объясняет 8 понятий, без которых невозможно осознанно выбрать железо и настройки.
Все цифры — для нашей модели **Qwen3.8-27B** (подробнее о ней — в [02-model.md](02-model.md)).

---

## 1.1. Веса и точность: сколько памяти занимает сама модель

Модель — это 27 млрд чисел («параметров», «весов»). Сколько они занимают, зависит от того,
сколькими битами хранится каждое число:

| Точность | Байт на параметр | Размер Qwen3.8-27B | Качество |
|---|---|---|---|
| BF16 (оригинал) | 2 | 55.6 ГБ | эталон |
| FP8 (официальная версия от Qwen) | 1 | 30.9 ГБ | практически без потерь |
| NVFP4 / INT4 (4 бита) | ~0.5 | 19.5–26.4 ГБ | небольшие потери, заметнее на сложных задачах |

Размеры 4-битных версий различаются, потому что часть слоёв (эмбеддинги, внимание) обычно оставляют в 8 или 16 битах.

**Итог:** FP8 — «золотая середина» для 27B: вдвое меньше памяти и быстрее, качество как у оригинала.

## 1.2. Два режима работы: префилл и декод

Каждый запрос к модели проходит две фазы:

1. **Префилл (prefill)** — модель «читает» весь промпт. Все токены обрабатываются параллельно,
   поэтому скорость упирается в **вычислительную мощность** GPU (TFLOPS). Это тысячи токенов в секунду.
   Результат префилла — «время до первого токена» (TTFT).
2. **Декод (decode)** — модель генерирует ответ **по одному токену**. На каждом шаге нужно прочитать
   из памяти **все веса модели и весь KV-кэш** (см. ниже). Поэтому скорость упирается
   в **пропускную способность памяти** (ТБ/с), а не в TFLOPS.

Пример на пальцах: у H200 память выдаёт 4.8 ТБ/с, веса FP8 — ~27 ГБ, которые читаются на каждом шаге.
Теоретический потолок ≈ 4800 / 27 ≈ 180 токенов/с на один поток, реально — примерно половина.

**Итог:** для генерации важна скорость памяти (ТБ/с), для чтения длинного контекста — TFLOPS.

## 1.3. Батчинг: почему 10 агентов почти так же быстры, как один

Когда 10 агентов генерируют одновременно, движок (vLLM) объединяет их в один «батч»:
веса читаются **один раз за шаг сразу для всех**. Поэтому суммарная скорость растёт почти
пропорционально числу агентов, пока не упрёмся в вычисления или в чтение KV-кэша.

Это главный экономический аргумент в пользу собственного сервера для роя агентов:
одна GPU обслуживает 10 агентов лишь немного медленнее, чем одного.

**Итог:** 10 параллельных агентов на одной мощной GPU — нормальный и эффективный режим.

---

## 1.4. KV-кэш — главный потребитель памяти при длинных контекстах

Чтобы не пересчитывать контекст на каждом шаге, модель хранит для каждого токена
промежуточные данные — «ключи и значения» (Key/Value) в слоях внимания. Это и есть **KV-кэш**.
Он растёт линейно с длиной контекста и **на каждом шаге декода читается целиком**.

Здесь нам сильно повезло с моделью. Qwen3.8-27B — **гибридная**:

- из 64 слоёв только **16** — классическое «полное внимание», им нужен KV-кэш;
- остальные **48** — Gated DeltaNet («линейное внимание»): у них вместо растущего кэша
  фиксированное состояние ≈ **75 МиБ на агента**, от длины контекста не зависит.

| | Обычная 32B-модель (Qwen3-32B) | Qwen3.8-27B |
|---|---|---|
| KV на 1 токен (BF16) | 256 КиБ | **64 КиБ** |
| KV на 1 токен (FP8) | 128 КиБ | **32 КиБ** |
| 1 агент × 256K токенов (FP8 KV) | 32 ГиБ | **8 ГиБ** |
| 10 агентов × 256K (FP8 KV) | 320 ГиБ | **80 ГиБ** |

Для 10 агентов с контекстом 256K нужно примерно **28 ГиБ весов FP8 + ~85 ГиБ KV-кэша ≈ 115–120 ГиБ**.
Именно отсюда вытекают требования к железу в [03-zhelezo.md](03-zhelezo.md).

Обратная сторона: при 250K контекста каждый агент добавляет ~8 ГиБ, которые нужно прочитать
**на каждом шаге декода**. Поэтому с ростом контекста генерация замедляется. Это физика,
её не обойти, только учитывать (см. калькулятор `scripts/vram_calc.py`).

**Итог:** гибридная архитектура делает задачу «10 × 250K» реальной на 1–2 GPU. У обычной модели
понадобилось бы в 4 раза больше памяти.

## 1.5. Кэш префиксов — почему повторный контекст почти бесплатен

Агент работает ходами. На каждом ходу в модель отправляется **вся история заново** плюс новый
кусок (результат инструмента, вопрос). Без кэша каждый ход пересчитывал бы все 250K токенов:
это десятки секунд и больше, даже на топовой GPU.

**Кэш префиксов** (prefix caching) решает это: если начало нового промпта совпадает с уже
посчитанным, движок берёт готовый результат из памяти и считает только новое.
Так же и между агентами: если у 10 агентов одинаковое начало (общий документ, кодовая база),
оно считается **один раз**.

Правила, чтобы кэш работал:
- общий большой контекст ставьте **в начало** промпта, личное для агента — **в конец**;
- начало промпта должно совпадать **до байта**: никаких дат/времени/случайных ID в system prompt;
- историю только **дописывайте**, не редактируйте старые сообщения.

Для гибридных моделей есть нюанс: состояние слоёв DeltaNet можно сохранить не в любой точке,
а только на границах блоков. Подробности и настройки — в [05-roy-agentov.md](05-roy-agentov.md).

**Итог:** правильный порядок сообщений и кэш префиксов — самая большая экономия во всём проекте.

## 1.6. Спекулятивное декодирование (MTP)

У Qwen3.8-27B есть встроенная маленькая «голова» MTP (multi-token prediction), которая угадывает
несколько следующих токенов. Основная модель проверяет эти догадки **за один шаг**. Совпало —
получили несколько токенов по цене одного.

- В vLLM включается одним флагом: `--speculative-config '{"method":"mtp","num_speculative_tokens":3}'`.
- В тестах vLLM доля принятых токенов 77–92% (зависит от точности весов и текста).
- При длинных контекстах выгода особенно велика: основная цена шага — чтение KV-кэша,
  а оно одинаково для 1 и для 4 проверяемых токенов.

**Итог:** MTP стоит включать. Проверяйте долю принятых токенов в метриках, а не на глаз.

## 1.7. Несколько GPU: TP или DP

- **Tensor Parallel (TP)** — одна копия модели «разрезана» на несколько GPU. Веса делятся,
  поэтому под KV-кэш остаётся больше места, а один поток генерирует быстрее. GPU постоянно
  обмениваются данными, поэтому лучше с NVLink, хотя на 2 картах работает и по PCIe.
- **Data Parallel (DP)** — на каждой GPU своя полная копия модели и свои агенты. Обмена нет,
  но каждая копия занимает память под веса, а кэш префиксов у копий раздельный.

Для 27B на двух GPU при длинных контекстах и общем префиксе у агентов **TP=2 выгоднее**:
примерно на 25% больше места под KV и один общий кэш префиксов.

---

## 1.8. Почему vLLM, а не Ollama / LM Studio

Ollama, LM Studio и llama.cpp отлично подходят для одного пользователя на домашнем ПК.
Для **10 параллельных агентов с длинными контекстами** нужен серверный движок:

- **непрерывный батчинг**: новые запросы вливаются в идущий батч без ожидания;
- **постраничный KV-кэш** (PagedAttention): память выделяется блоками, не резервируется «на максимум»;
- **кэш префиксов**, **FP8 KV-кэш**, **MTP**, метрики Prometheus;
- **OpenAI-совместимый API**: любой агентный фреймворк подключается сменой `base_url`.

Основной выбор — **vLLM**, альтернатива — **SGLang** (сравнение в [04-zapusk.md](04-zapusk.md)).

## Словарь

| Термин | Что это |
|---|---|
| Токен | кусочек текста, ~¾ английского слова; русский текст «дороже» в токенах |
| Контекст | всё, что модель видит в запросе: system prompt, история, документы |
| TTFT | time to first token — сколько ждать первого токена ответа |
| ток/с | токенов в секунду: на один поток (агента) или суммарно на сервер |
| KV-кэш | память под «ключи/значения» уже прочитанных токенов |
| Префилл / декод | чтение промпта / генерация ответа |
| Кэш префиксов | повторное использование KV для совпадающего начала промпта |
| MTP | встроенное спекулятивное декодирование, ускоряет генерацию |
| TP / DP | разрезать модель на несколько GPU / запустить несколько копий |
| Квантизация | хранение весов в меньшем числе бит (FP8, NVFP4, INT4) |
