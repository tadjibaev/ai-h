# 5. Рой агентов: как организовать работу, чтобы было быстро и дёшево

Сервер с моделью — это половина дела. Вторая половина — **как агенты формируют запросы**.
От этого скорость и стоимость меняются в разы, причём бесплатно.

---

## 5.1. Четыре схемы роя

| Схема | Как устроена | Когда использовать |
|---|---|---|
| **Общий контекст → веер задач** (`shared`) | Все агенты получают один и тот же большой контекст (кодовая база, пачка документов) и разные подзадачи. Потом сборщик объединяет ответы | анализ одного большого массива с разных сторон: риски, баги, требования, сводки |
| **Map-reduce** (`map`) | Материал делится на части, каждый агент читает свою, сборщик объединяет | материала больше, чем влезает в один контекст (>250K) |
| **Конвейер** | Агент A → агент B → агент C (план → исполнение → проверка) | многоэтапная обработка, где этапы зависят друг от друга |
| **Долгоживущие агенты с инструментами** | Каждый агент — цикл «подумал → вызвал инструмент → получил результат → дальше», контекст растёт до 100–250K | кодинг-агенты, исследовательские агенты, автоматизация |

Первые две схемы реализованы в `scripts/swarm_demo.py`, это готовая отправная точка:

```bash
# 10 агентов анализируют один проект с разных сторон
python3 scripts/swarm_demo.py --mode shared --context ./my_project \
    --task "Найди главные риски, ошибки и узкие места" --agents 10 --out report.md

# материалы делятся между 10 агентами, потом сводятся
python3 scripts/swarm_demo.py --mode map --context ./docs --task "Сделай сводку по всем документам" --agents 10
```

## 5.2. Главное правило: одинаковое начало промпта

Движок переиспользует уже посчитанный KV-кэш, только если **начало промпта совпадает до токена**.
Отсюда правила:

1. **Большое и общее — в начало, личное — в конец.**
   `system: [инструкции] + [общий контекст 200K]` → `user: [подзадача агента]`.
   Тогда 200K считаются один раз на всех, а для каждого агента — только его подзадача.
2. **Никакой «динамики» в начале**: дата и время, случайные ID, счётчики, имя агента в первой строке
   system prompt ломают совпадение. Всё переменное — после общего блока.
3. **Детерминированный порядок**: файлы в контексте всегда в одном порядке (например, по имени).
4. **История только дописывается.** Если агент «сжимает» или правит старые сообщения, всё,
   что после правки, пересчитывается заново. Сжимайте редко и крупно (см. 5.5).
5. **Прогрев.** Если 10 агентов стартуют одновременно с одинаковым префиксом, движок может
   начать считать его 10 раз параллельно: кэш появляется только после того, как блок посчитан.
   Надёжнее сначала отправить **один** запрос с общим префиксом (`max_tokens=1`), дождаться его,
   и только потом запускать агентов. В `swarm_demo.py` и `bench_swarm.py --warmup` так и сделано.

## 5.3. Сколько агентов запускать одновременно

- **Память**: все одновременно активные агенты должны поместиться в KV-кэш
  (`Maximum concurrency` в логе vLLM, см. 7.2). Иначе будут вытеснения, а это хуже, чем очередь.
- **Скорость**: с ростом числа агентов суммарная скорость растёт, а скорость каждого падает.
  При длинных контекстах основная нагрузка — чтение KV-кэша всех агентов на каждом шаге.
- **Практика**: ограничьте параллелизм **на стороне клиента** (семафор на 10, как в `swarm_demo.py`)
  и поставьте `--max-num-seqs` на сервере с небольшим запасом (16). Лишние запросы подождут в очереди
  клиента, а не будут бороться за память сервера.

## 5.4. Режим размышлений (thinking): тратит время

Qwen3.8 по умолчанию «думает» перед ответом (блок `<think>`), и это тысячи токенов генерации.
Для роя это главный регулятор между качеством и скоростью:

| Настройка (в запросе) | Когда |
|---|---|
| `"chat_template_kwargs": {"enable_thinking": false}` | простые подзадачи: извлечь, пересказать, отформатировать, классифицировать |
| `"chat_template_kwargs": {"reasoning_effort": "low"}` | большинство рабочих подзадач: адаптивное короткое размышление (Qwen3.8) |
| `"reasoning_effort": "medium"` / по умолчанию (`xhigh`) | планировщик, сборщик, сложный анализ, отладка |

В скриптах это флаг `--thinking off|low|medium|high|xhigh`. Хорошая схема: исполнители на `low`,
планировщик и сборщик на полном размышлении.

На сервере обязательно `--reasoning-parser qwen3`. Тогда размышления приходят отдельным полем,
а в `content` остаётся чистый ответ (иначе `<think>...</think>` попадёт в текст ответа).

## 5.5. Управление контекстом долгоживущих агентов

Контекст 262K — предел модели (нативно). Но скорость декода падает с ростом контекста,
а память кончается раньше, если все 10 агентов одновременно на пределе. Практика:

- держите рабочий контекст агента **в пределах 100–200K**, а 262K — как аварийный запас;
- большие результаты инструментов (логи, выгрузки) **обрезайте и резюмируйте** до передачи агенту;
- при приближении к порогу делайте **сжатие**: один запрос «подведи итоги работы» → новая сессия
  начинается с `[system + общий контекст] + [итоги]`. Общий префикс при этом снова берётся из кэша;
- не держите «мёртвые» сессии: запрос завершился, и его KV-блоки становятся кэшем, который
  вытесняется по мере нужды. Активной памяти он не занимает.

Контекст до ~1M токенов возможен через YaRN (см. [02-model.md](02-model.md)), но для роя это почти
всегда плохая сделка: память и скорость падают пропорционально длине, а качество на коротких
запросах немного снижается.

## 5.6. Готовые агентные инструменты с локальной моделью

Сервер vLLM говорит на языке OpenAI API, поэтому подключается к чему угодно. Нужны три параметра:

| Параметр | Значение |
|---|---|
| Base URL | `http://<адрес-сервера>:8000/v1` |
| API key | значение `API_KEY` из запуска сервера (или любое, если ключ не задан) |
| Model | `qwen3.8-27b` (имя из `--served-model-name`) |

### Qwen Code (официальный агент от Qwen, аналог Claude Code)

Умеет субагентов и «команды агентов», есть headless-режим `qwen -p "..."` для скриптов.
Конфиг `~/.qwen/settings.json`:

```json
{
  "env": { "LOCAL_VLLM_KEY": "ваш-API_KEY" },
  "modelProviders": {
    "openai": [
      {
        "id": "qwen3.8-27b",
        "name": "Qwen3.8-27B (свой vLLM)",
        "envKey": "LOCAL_VLLM_KEY",
        "baseUrl": "http://<адрес-сервера>:8000/v1",
        "generationConfig": {
          "timeout": 600000,
          "contextWindowSize": 262144,
          "samplingParams": { "temperature": 1.0, "top_p": 0.95, "max_tokens": 32768 }
        }
      }
    ]
  },
  "security": { "auth": { "selectedType": "openai" } },
  "model": { "name": "qwen3.8-27b" }
}
```

Режим размышлений для vLLM задаётся через `"extra_body": {"chat_template_kwargs": {"enable_thinking": false}}`
в `generationConfig`, а не через `enable_thinking` верхнего уровня: так делает облачный API Qwen,
vLLM это поле проигнорирует.

Рой из 10 параллельных headless-агентов, каждый в своей папке или ветке:

```bash
for i in $(seq 1 10); do
  (cd "work/agent-$i" && qwen -p "$(cat ../../tasks/task-$i.md)" > ../../logs/agent-$i.log 2>&1) &
done
wait
```

### Другие

Любой инструмент с пунктом «OpenAI-compatible / Custom provider» (opencode, Cline/Roo/Kilo Code,
Aider, LangGraph, OpenAI Agents SDK, CrewAI и т.д.) подключается теми же тремя параметрами.
Если в настройках есть «context window», ставьте 262144; если «max output tokens», то 16–32K
(с размышлениями ответы длинные).

**Порты:** многие инструменты (например, веб-интерфейс OpenHands) по умолчанию тоже занимают 8000.
Если они на одной машине с vLLM, запустите vLLM на другом порту (`PORT=8001`).

## 5.7. Чек-лист перед запуском роя

- [ ] Общий контекст в начале, одинаковый до байта; личное — в конце.
- [ ] Прогрев общего префикса перед стартом агентов.
- [ ] Параллелизм на клиенте ≤ `Maximum concurrency` из лога vLLM.
- [ ] Для простых подзадач — `enable_thinking: false` или `reasoning_effort: low`.
- [ ] Большие результаты инструментов обрезаются и резюмируются.
- [ ] `bench_swarm.py` показывает 80%+ из кэша на повторных ходах и 0 вытеснений.
